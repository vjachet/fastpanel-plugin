# fastpanel-accounts — пользователи только по id

```bash
SCRIPT="${CLAUDE_PLUGIN_ROOT}/skills/fastpanel-accounts/scripts/fastpanel_accounts.py"
python3 "$SCRIPT" list
python3 "$SCRIPT" whoami [-A ID_АККАУНТА]
python3 "$SCRIPT" users [-A ID_АККАУНТА]
python3 "$SCRIPT" add --request ID_ЗАЯВКИ [-A ID_АККАУНТА] [--quota N] [--wait N]
python3 "$SCRIPT" ssh-keys ID_ПОЛЬЗОВАТЕЛЯ [-A ID_АККАУНТА]
python3 "$SCRIPT" ssh-status ID_ПОЛЬЗОВАТЕЛЯ [-A ID_АККАУНТА]
python3 "$SCRIPT" ssh-add ID_ПОЛЬЗОВАТЕЛЯ --key-file ПУТЬ.pub [-A ID_АККАУНТА] [--desc ОПИСАНИЕ] [--wait N]
```

## Имена остаются локально

Агент выбирает пользователя только по числовому id. Не проси логин, не передавай его
в аргументах, вопросах или отчётах. В `-A` передавай только непрозрачный id аккаунта из `list`.
Локальные name/label, адрес панели, пути, роли, квоты, отпечатки, комментарии
и содержимое ключей в ответах этих команд не выдаются.

Ответы — компактный JSON с разрешёнными полями:

| Команда | Данные для агента |
|---|---|
| `list` | `account_ids` |
| `whoami` | `user_id` |
| `users` | `user_ids`, доступные владельцы `owner_ids` |
| `prepare-user` (только человек) | `request_id` |
| `add`, `ssh-add` | `status`, `user_id` |
| `ssh-keys` | `user_id`, `key_ids` |
| `ssh-status` | `user_id`, `ssh_ready`; при отказе `reason` |
| Ошибка | `status: "error"`, фиксированный `code` |

Для внешнего отчёта передавай только итог, целевой id и необходимую причину отказа.
Не добавляй данные из старой переписки, не запрашивай расширенный вывод и не обходи
проекцию через импорт ядра или прямой API. Например: `{"status":"added","user_id":93}`.
Если человек знает только свой локальный псевдоним аккаунта, он сам запускает
`account-id -A ПСЕВДОНИМ` в своём терминале и передаёт агенту полученный `account_ids`.

Скрипты разрешают id в логин внутри процесса и передают его только собственной панели,
когда этого требует API. Логины всех видимых пользователей, включая администратора,
скрываются в stdout/stderr, в том числе в путях, JSON-экранировании и URL-кодировании.
Свободный текст ошибок панели и исключений не выводится: он может содержать имя
пользователя, которого аккаунт не видит. Не восстанавливай скрытое значение по пути или данным.

Конфиг, заявки и доступы в `~/.config/fastpanel/`, кеш в `~/.cache/fastpanel/` агент
не читает. Используй только скрипты плагина; правила — `${CLAUDE_PLUGIN_ROOT}/SETUP.md`.
Если доступы не настроены, направь человека к INSTALL.md для локальной настройки.
Если аккаунтов несколько и нужный неизвестен, покажи `list` и запроси выбор.
Перед изменением назови id аккаунта и id пользователя (для создания — id заявки).
Подробная диагностика остаётся в локальном защищённом `diagnostics/last-error.json`
в каталоге конфига. Агент не читает и не пересылает этот файл.

## Создание пользователя без раскрытия имени

Человек запускает **в своём локальном терминале, вне агента**:

```bash
python3 "$SCRIPT" prepare-user
```

Команда спрашивает новый логин без отображения ввода, сохраняет его в
`~/.config/fastpanel/user-requests/<32 hex символа>.json` (`600`) и печатает только id заявки.
Агент не запускает `prepare-user`, не заполняет этот файл, не читает его и не просит имя
в переписке. Если заявки нет, объясни этот шаг пользователю и попроси только её id.
Вызов без интерактивного терминала отклоняется.

Получив id заявки, агент запускает `add --request ID`. Выбранный аккаунт должен иметь
право создавать пользователей. Создаётся только `ROLE_USER`, через `POST /api/users`
с username из локальной заявки, сгенерированным паролем и quota. `--owner` не нужен.
Квота по умолчанию `0`; целое неотрицательное значение передаётся без пересчёта единиц.
Шаблоны лимитов не реализованы. Если создание с этими параметрами уже запрошено,
дополнительное подтверждение не требуется.

Логин уже есть — `status: "exists"` и код `0`, его пароль, роль и квота не меняются.
Иначе доступы сохраняются **до POST** в
`~/.config/fastpanel/users/<аккаунт>/user-<случайный суффикс>.json` (`600`): url, username,
password, request_id. При `FASTPANEL_CONFIG_DIR` используется этот каталог. Пароль — 24 случайных
символа. Старые файлы не перезаписываются; в `config.json` новый аккаунт не добавляется.
Агент видит только результат и id пользователя. Путь не выводится; человек находит
локальный файл по сохранённому `request_id`, не отправляя его содержимое агенту.

После POST скрипт до `--wait` секунд (по умолчанию 60) ждёт пользователя без `action`
в `/api/users`. Ошибка сети/тайм-аут не доказывает, что пользователь не создан: сохрани
доступы, сначала прочитай `users`, не повторяй POST вслепую. После отказа файл содержит
лишь доступы из попытки. Конкурирующий запрос занял имя — код `3`, эти доступы к нему
не относятся. Коды `0` — создан/уже был; `1` — ошибка/не подтверждён; `2` — аргументы.

## SSH-доступ пользователя

Пользователь выбирается только по положительному числовому id из `users`.
Логины и имена настроенных аккаунтов для выбора пользователя не принимаются.
Нужны права панели на SSH-ключи выбранного пользователя.

```bash
python3 "$SCRIPT" ssh-status 93 -A acc-1a2b3c4d
python3 "$SCRIPT" ssh-keys 93 -A acc-1a2b3c4d
python3 "$SCRIPT" ssh-add 93 -A acc-1a2b3c4d --key-file ~/.ssh/id_ed25519.pub
```

`--key-file` и `--key` взаимоисключающие; предпочитай файл, чтобы комментарий ключа
оставался локально. Принимается одна строка публичного OpenSSH-ключа: тип, base64,
необязательный комментарий. Приватные ключи, несколько ключей и опции authorized_keys
не принимаются. Не читай и не проси приватный ключ. Описание `--desc` по умолчанию —
комментарий публичного ключа. Не включай имена пользователей в описание, передаваемое агентом.

Скрипт читает `/api/users/<id>`, проверяет `enabled: true` и `ssh_access: true`, сам
получает логин и обращается к `/api/sshd/<внутренний логин>/auth_keys`.
Сравнение ключа идёт по декодированным данным без комментария. Активный существующий
ключ — `status: "exists"`, без POST. Отключённый или ожидающий обработки ключ — ошибка,
без дублирования или изменения настроек.

Новый ключ добавляется в `/api/sshd/<внутренний логин>/auth_key` телом
`{"type":1,"raw_key":"<публичный ключ>","desc":"<описание>"}`.
До `--wait` секунд (по умолчанию 60) скрипт ждёт включённый ключ без `action`, потом
ещё раз проверяет SSH-доступ. Отчёт: `status: "added"` и id пользователя.
Включение SSH-доступа, сертификаты, ограничения IP, правка и удаление ключей не реализованы.
После ошибки/потери ответа сначала `ssh-status` и `ssh-keys`, не повторяй POST вслепую.
Примеры запросов при разработке не разрешают изменение живой панели.

`ssh-status` показывает id и готовность `ssh_ready`; при отказе — фиксированную причину
`user_disabled`, `ssh_disabled`, `state_unknown` или `no_active_key`;
код `0` — условия в панели выполнены, `1` — нет/ошибка. Это не попытка SSH-входа.
Человек узнаёт логин и формирует команду подключения у себя локально. Агент не печатает
команду с настоящим логином и не подставляет его в SSH-аргументы.
